# index-db v0.3.0 — Deletion and range scans

**The ordered-map surface, completed.** v0.2.0 gave the tree its shape — keys
stored in order, splitting and growing on insert. v0.3.0 gives it the two things
that make it an index you can actually build on: you can take entries out, with
the tree rebalancing itself to stay shallow, and you can scan a key range, the
single operation a B+tree exists for that a hash map cannot do. Forward, reverse,
bounded, open-ended — all in order, all lazy.

## What is index-db?

A B+tree indexing primitive for storage engines: ordered keys mapped to values,
with fast point lookups, ordered iteration, and range scans, laid out as a tree
of fixed-fan-out nodes rather than on the heap. The node layout is the one a
storage engine persists as an on-disk index; this release keeps the tree in
memory.

## What's new in 0.3.0

### `remove` — delete with self-rebalancing

```rust
use index_db::BPlusTree;

let mut index = BPlusTree::new();
index.insert(1_u32, "a");
index.insert(2, "b");

assert_eq!(index.remove(&1), Some("a")); // returns the value that was there
assert_eq!(index.remove(&1), None);       // already gone
```

Deletion is where a B+tree earns its keep. Removing an entry can leave a node
below half full; rather than let the tree degrade, the node borrows a single
entry from a sibling that has one to spare, or — if neither sibling does — merges
with one, folding the separator between them back in. A merge removes a separator
from the parent, which can cascade the rebalancing upward; when the root is left
with a single child, the tree collapses a level. The result is that after any
sequence of inserts and deletes every leaf is still at the same depth and every
non-root node is still at least half full. The mixed-workload property test
asserts exactly that — balance and minimum occupancy — after *every* operation,
cross-checked against `BTreeMap`.

### `iter` and `range` — ordered and bounded scans

```rust
use index_db::BPlusTree;

let mut index = BPlusTree::new();
for k in 0..10_u32 {
    index.insert(k, k);
}

// A half-open window, in order.
let window: Vec<_> = index.range(3..7).map(|(&k, _)| k).collect();
assert_eq!(window, vec![3, 4, 5, 6]);

// The same range, in reverse.
let rev: Vec<_> = index.range(3..7).rev().map(|(&k, _)| k).collect();
assert_eq!(rev, vec![6, 5, 4, 3]);
```

`iter` walks every entry in ascending key order; `range` walks the slice of
entries inside any standard range expression — `a..b`, `a..=b`, `..b`, `a..`, or
`..`. Both return one iterator type, [`Iter`], which is a `DoubleEndedIterator`,
so `.rev()` gives descending order and the iterator can be consumed from both
ends until they meet. The scan is lazy: it seeks to the start in `O(log n)` and
then yields each entry in amortized constant time, without materializing the
range. `&tree` implements `IntoIterator`, so `for (k, v) in &tree` works too.

Iteration walks the tree with an explicit cursor — a path from the root to the
current leaf — rather than threaded leaf links, which keeps the node layout free
of the back-pointers that complicate a persisted, concurrently-traversed tree
later on.

## Performance

Measured with Criterion on Windows x86_64 (release, single thread):

| Operation | Cost |
|-----------|------|
| `range` scan, 1,000-entry window (10K-entry tree) | ~0.82 µs |
| `range` scan, 1,000-entry window (1M-entry tree) | ~1.9 µs |
| `remove`, per entry (1K-entry tree, remove all) | ~33 ns |
| `remove`, per entry (100K-entry tree, remove all) | ~53 ns |

A range scan costs about a nanosecond per entry it yields, and its cost tracks
the window width rather than the tree size — the seek to the start is the only
part that grows with `n`. Point lookups are unchanged from v0.2.0 (~10–52 ns
across 1K–1M entries). Benchmarks live in `benches/index_bench.rs`.

## Breaking changes

**None.** Everything in this release is additive: three new methods, one new
public iterator type, and an `IntoIterator` impl for `&BPlusTree`.
