# index-db v0.5.0 — Hardening and API freeze

**The surface is locked.** v0.5.0 adds no public API. It pins the in-memory tree
against adversarial key distributions and large-scale churn, demonstrates that
many threads can read it at once, and freezes the public API ahead of 1.0. From
here the remaining pre-1.0 work is the page-backed backend and the soak to a
stable release.

## What is index-db?

A B+tree indexing primitive for storage engines: ordered keys mapped to values,
with fast point lookups, ordered iteration, range scans, and bulk loading.

## What's new in 0.5.0

### Adversarial key distributions

A B+tree's structural maintenance — splitting on insert, borrowing and merging on
delete, collapsing the root — is most likely to break under orderings that push
all the work to one side. The new tests drive exactly those:

- ascending inserts followed by descending deletes, and the reverse, across a
  range of small orders, so every delete cascades merges up one edge of the tree;
- a zigzag insert (both ends toward the middle) paired with a middle-out delete;
- keys clustered into a narrow band, so most splits land in one subtree before the
  tree balances;
- repeated full-range overwrites, confirming length and values stay correct and
  `clear` returns the tree to a single leaf.

Each checks the structural invariants — balanced height, sorted keys, routing
separators, minimum occupancy — after *every* delete, and the final contents
against a reference set. A small-order adversarial property test does the same
over randomized insert/delete streams in a deliberately cramped key space.

### Large-scale and concurrent stress

`tests/stress.rs` works the tree the way a consumer would, at size:

- 50,000 scattered inserts then scattered deletes, with a full scan checked
  against `BTreeMap` at each stage and the tree emptied back to a single leaf;
- sustained insert/delete churn over a bounded key space, verified wave by wave;
- a 30,000-entry bulk load followed by heavy scattered deletion;
- adversarial string keys sharing long common prefixes and varying in length.

And concurrency — the part the in-memory tree actually has today. The tree is
`Sync`, so reads need no lock: `get`, `iter`, and `range` all take `&self`. The
concurrent-reader test runs eight threads traversing one shared tree at once —
point lookups across the whole key space, full scans that sum to the same total
from every thread, and forward/reverse ranges that agree. It does not compile
unless `BPlusTree` is `Sync`. Write-side concurrency belongs to the page-backed
backend, where latches live on the pager's frames.

### API freeze

The public surface is frozen as of this release:

- `BPlusTree<K, V>`: `new`, `from_sorted`, `insert`, `get`, `contains_key`,
  `remove`, `iter`, `range`, `len`, `is_empty`, `height`, `clear`.
- Trait impls: `Default`, `IntoIterator for &BPlusTree`.
- `Iter<'a, K, V>`: `Iterator` + `DoubleEndedIterator`, item `(&K, &V)`.

The only change planned before 1.0 is an additive, defaulted store type parameter
on `BPlusTree` and `Iter` when the page-backed backend lands — a non-breaking
addition for existing `BPlusTree<K, V>` code.

## Breaking changes

**None.** This release is tests and documentation only.

## Verification

Run on Windows x86_64 and Linux (WSL2 Ubuntu), Rust stable and MSRV 1.85.0;
macOS is covered by the CI matrix:

```bash
cargo fmt --all -- --check
cargo clippy --all-targets -- -D warnings
cargo clippy --all-targets --all-features -- -D warnings
cargo test
cargo test --all-features
cargo build --examples
cargo build --no-default-features
RUSTDOCFLAGS="-D warnings" cargo doc --no-deps --all-features
cargo +1.85 test --all-features
cargo audit
cargo deny check
```

All green on both platforms. Counts at this tag: 24 unit tests (including the
adversarial and small-order property tests), 11 integration tests, 5 stress tests
(including the eight-thread concurrent-reader test), and 15 doctests.

## What's next

- **Page-backed backend.** A `PageStore` behind the storage seam, with latch
  coupling (crabbing) over `page-db`'s page guards — the concurrent, persistent
  tree, loom-checked. Blocked on `page-db` publication.
- **0.6.0 → 1.0.0.** Alpha / beta / RC: integrate against real consumers, capture
  final benchmarks, then the 1.0 freeze and publish.
