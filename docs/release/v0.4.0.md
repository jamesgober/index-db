# index-db v0.4.0 — Bulk load and the storage seam

**The in-memory tree, feature-frozen — and set up for what comes next.** v0.4.0
adds bulk construction from sorted input and, underneath, refactors the tree so
its nodes are reached through an internal storage seam rather than owned inline.
That second change is the quiet but important one: it is what lets the concurrent,
page-backed B+tree be *added* later instead of *rewritten*. The in-memory
ordered-map surface is now feature-frozen.

## What is index-db?

A B+tree indexing primitive for storage engines: ordered keys mapped to values,
with fast point lookups, ordered iteration, range scans, and now bulk loading,
laid out as a tree of fixed-fan-out nodes.

## What's new in 0.4.0

### `from_sorted` — bulk construction

```rust
use index_db::BPlusTree;

let index = BPlusTree::from_sorted((0..1_000_000_u32).map(|k| (k, k)));
assert_eq!(index.len(), 1_000_000);
assert_eq!(index.height(), 4);
```

When the input is already sorted by key, building the tree bottom-up — packing
leaves and laying down the levels above them in one pass — is far faster than
inserting a million times and splitting along the way. `from_sorted` takes any
iterator of `(key, value)`; if the keys turn out not to be strictly ascending it
falls back to ordinary insertion, so the result is always a correct tree and only
the fast path depends on the precondition. The keys of a `BTreeMap`, or a sorted
scan of another store, load directly.

### The storage seam

The larger change is invisible from the outside. The tree no longer owns its
nodes inline; it addresses them by id through an internal node store, and the
search / insert / delete / bulk-load logic is written against that store rather
than against a concrete layout. The in-memory store — a heap slab with a free
list — is the only backend today.

The point is the *next* backend. A B+tree becomes concurrent and persistent by
putting its nodes on pages and latching those pages as you traverse; `page-db`
already provides exactly that — pinned page frames with latches, loom-checked.
index-db's job is only the crabbing protocol over those guards. Because the tree
algorithm now speaks ids and goes through the store, that page-backed backend
slots in behind the same seam without touching the algorithm. (See the roadmap
for why this is the right layer for concurrency, rather than hand-rolled locks on
heap nodes.)

### Feature freeze

The in-memory public surface — `new`, `from_sorted`, `insert`, `get`,
`contains_key`, `remove`, `iter`, `range`, `len`, `is_empty`, `height`, `clear`,
the `Iter` iterator, and `IntoIterator for &BPlusTree` — is feature-frozen. The
remaining pre-1.0 work is hardening, the page-backed backend, and the API freeze.

## Performance

The seam is not free. Reaching a node by id costs one extra memory indirection
per level versus an inline child, which shows up on point lookups at large sizes.
Measured with Criterion on Windows x86_64 (release, single thread):

| Operation | v0.3.0 (inline) | v0.4.0 (id-addressed) |
|-----------|-----------------|-----------------------|
| `get`, 1K entries | ~9.8 ns | ~11.7 ns |
| `get`, 100K entries | ~26 ns | ~34 ns |
| `get`, 1M entries | ~52 ns | ~79 ns |
| `range`, 1K window over 1M | ~1.9 µs | ~2.0 µs |
| `remove`, per entry (100K) | ~53 ns | ~56 ns |

Range scans and deletes are essentially unchanged; point lookups pay the
indirection, more so as the tree outgrows cache. This is a deliberate trade: the
page-backed backend is id-addressed by nature, so the seam is a cost index-db
would pay there regardless, and paying it now is what keeps that backend additive.
The absolute numbers remain well inside what a B-tree index needs. Benchmarks live
in `benches/index_bench.rs`.

## Breaking changes

**None.** `from_sorted` is additive, and the storage refactor is internal — the
public API is unchanged.

## Verification

Run on Windows x86_64 and Linux (WSL2 Ubuntu), Rust stable and MSRV 1.85.0;
macOS is covered by the CI matrix:

```bash
cargo fmt --all -- --check
cargo clippy --all-targets -- -D warnings
cargo clippy --all-targets --all-features -- -D warnings
cargo test
cargo test --all-features
cargo build --examples
cargo build --no-default-features
RUSTDOCFLAGS="-D warnings" cargo doc --no-deps --all-features
cargo +1.85 test --all-features
cargo audit
cargo deny check
```

All green on both platforms. The same property tests that pin the tree against
`BTreeMap` — point operations, mixed insert/remove with the balance and
minimum-occupancy invariants checked after every step, iteration, and ranges —
pass unchanged over the refactored storage, plus a new property test that the
bulk-loaded tree matches an insert-built one. Counts at this tag: 18 unit tests,
11 integration tests, and 15 doctests.

## What's next

- **Hardening.** Adversarial key distributions and concurrent-traversal stress,
  then the public API freeze.
- **Page-backed backend.** A `PageStore` behind the storage seam, with latch
  coupling (crabbing) over `page-db`'s page guards — the concurrent, persistent
  tree. Blocked on `page-db` publication.
