# index-db v1.0.1: documentation corrections and a panic-safety fix

A patch release. The API is unchanged and the minimum Rust version stays 1.85.

## What index-db 1.0 is

An in-memory B+tree ordered map: point lookups, inserts and removes in
logarithmic time, forward and reverse range scans, and bulk construction from
sorted input. The tree is `Sync`, so any number of threads can read it at once;
`insert`, `remove` and `clear` take `&mut self`, so concurrent writers need a
lock around the whole tree. Nothing is persisted: the tree lives on the heap and
is gone when the process exits.

The 1.0 README, crate docs and crates.io description said otherwise: that the
tree is laid out over paged storage, persists through a pager, and lets many
readers and writers traverse it at once through latch coupling. Those describe
the planned page-backed backend over `page-db`, which is not part of 1.0. The
docs and the description now describe what ships and mark that backend as
planned.

## Fixes

- **Panic safety.** If a key type's `Clone` panicked while `insert` split a
  leaf or `remove` borrowed from a sibling, and the caller caught the panic and
  kept using the tree, the tree could be left inconsistent: an entry visible to
  `iter` but not to `get`, a wrong `len`, and a duplicate after re-inserting the
  key. Separator keys are now cloned before any entry moves, and `len` is
  updated as soon as an entry leaves its leaf, so a panicking clone leaves a
  consistent tree.
- **Allocation docs.** The complexity table said `new` allocates nothing, that
  `insert` allocates only on a node split, and that `remove` never allocates.
  `new` makes one small allocation, inserts also allocate when a node's arrays
  grow, and removes allocate occasionally during merges. The table now says so.
- **Node ids** are range-checked when assigned, so the node store fails loudly
  at its 2^32-node limit instead of reusing an id.
- **Tests without `std`.** `cargo test --no-default-features` compiles again.

## Documented behaviour

- `range` with a start after its end (`50..10`) yields nothing rather than
  panicking as `BTreeMap::range` does.
- `from_sorted` collects its input into a `Vec` to check the order, and falls
  back to one insert per entry on unsorted input without reporting it.
- `clear` keeps the node storage's capacity for reuse.

The unused `loom` dev-dependency was removed.
