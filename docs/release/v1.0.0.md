# index-db v1.0.0 — Stable

**The first stable release.** index-db 1.0 is a B+tree indexing primitive: an
ordered map that keeps its keys sorted across a tree of fixed-fan-out nodes, with
fast point lookups, deletion that keeps the tree balanced, forward and reverse
range scans, and bulk construction from sorted input. The public API is frozen
until 2.0. It has no runtime dependencies, is `no_std`-compatible, and is `Sync`
so any number of threads can read it at once.

## What is index-db?

The ordered-access and secondary-index layer a storage engine builds on: keys
mapped to values in sorted order, point lookups and range scans in logarithmic
time, laid out as a tree of fixed-fan-out nodes that stays balanced on its own
through splits, borrows, and merges.

## The stable surface

```rust
use index_db::BPlusTree;

let mut index = BPlusTree::new();
index.insert(3_u32, "three");
index.insert(1, "one");
index.insert(2, "two");

assert_eq!(index.get(&2), Some(&"two"));
let keys: Vec<_> = index.range(1..3).map(|(&k, _)| k).collect();
assert_eq!(keys, vec![1, 2]);
assert_eq!(index.remove(&2), Some("two"));
```

Frozen until 2.0:

- `BPlusTree<K, V>`: `new`, `from_sorted`, `insert`, `get`, `contains_key`,
  `remove`, `iter`, `range`, `len`, `is_empty`, `height`, `clear`.
- Trait impls: `Default`, `IntoIterator for &BPlusTree`.
- `Iter<'a, K, V>`: `Iterator` + `DoubleEndedIterator` over `(&K, &V)`.

`K` is `Ord`; `insert`, `remove`, and `from_sorted` also need `K: Clone` (a B+tree
copies separator keys between nodes). Values carry no bounds.

## What changed for 1.0

The inert `serde` feature and its optional dependency were removed. The feature
gated no code — there was never a `Serialize`/`Deserialize` implementation — and
serde is not index-db's persistence path; the page-backed backend is. With it
gone, **index-db has no runtime dependencies**.

## Definition of done

This release was audited against the project's definition of done.

- **Compiles clean** on Windows, Linux (WSL2), and macOS (CI), on stable and the
  1.85 MSRV, with `-D warnings`.
- **`fmt`, `clippy` (default and all features), `cargo doc -D warnings`** all
  clean. **`cargo audit` and `cargo deny check`** pass.
- **No `unwrap` / `expect` / `todo!` / `unimplemented!` / `dbg!`** in shipping
  code; `#![forbid(unsafe_code)]` — there is no `unsafe` in the crate at all.
- **Every public item has rustdoc with a runnable example** (15 doctests).
- **The B+tree invariants are property-tested** — sorted keys, balanced height,
  routing separators, and minimum node occupancy are checked after every insert
  and delete, cross-checked against `std::collections::BTreeMap`, including over
  adversarial key distributions and a 200,000-operation soak.
- **Hot paths are benchmarked** with Criterion; baselines are recorded in
  `docs/PERFORMANCE.md`.

### Concurrency, and what 1.0 does not include

index-db's design splits responsibility cleanly: the *algorithm* is in this crate,
and *where the nodes live* is a storage seam. The 1.0 backend is in-memory, and
because reads take `&self` over immutable data, the tree is `Sync` — many threads
read one shared tree with no locking, which the test suite exercises directly.

Write-side concurrency belongs to the **page-backed backend**: a `PageStore`
behind the same seam, where a node is a `page-db` page and concurrent access is
latch coupling (crabbing) over the pager's already-loom-checked frame guards.
Because the tree algorithm already speaks node ids through the seam, that backend
is an **additive 1.x release** — a defaulted store type parameter, non-breaking
for `BPlusTree<K, V>` code written against 1.0. It is not in this release.

## Performance

Single-machine, single-thread, release build (see `docs/PERFORMANCE.md`):

| Operation | 1K entries | 100K | 1M |
|-----------|-----------:|-----:|---:|
| `get` | ~12 ns | ~35 ns | ~80 ns |
| `insert` (amortized) | ~20 ns | ~44 ns | — |
| `remove` (amortized) | ~38 ns | ~62 ns | — |

Range scans cost about a nanosecond per entry yielded and track the window width,
not the tree size. Point-lookup growth at scale is cache behaviour — the height
moves only from 2 to 4 levels across a thousandfold size increase.

## Breaking changes

The `serde` feature was removed. index-db was not previously published, so no
released version is affected.
