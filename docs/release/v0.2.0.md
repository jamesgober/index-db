# index-db v0.2.0 — B+tree core

**The hard part, and it was not deferred.** v0.2.0 lands the engine of the
library: the B+tree itself. Keys are stored in sorted order across a tree of
fixed-fan-out nodes, point lookups run in logarithmic time, and the tree splits
its nodes and grows taller on its own as it fills — staying balanced at every
depth with no rebalancing pass and no caller involvement. This is the structure
every other capability on the roadmap builds on, so it shipped first.

## What is index-db?

A B+tree indexing primitive for storage engines: ordered keys mapped to values,
with fast point lookups, laid out as a tree of fixed-fan-out nodes rather than on
the heap one entry at a time. The node layout — sorted keys packed into
fixed-capacity arrays, internal nodes routing to their children — is the one a
storage engine persists as an on-disk index. This release keeps the tree in
memory; the layout is the durable one a pager will later back.

## What's new in 0.2.0

### `BPlusTree<K, V>` — the ordered map

One public type, an ordered map with a deliberately small surface:

```rust
use index_db::BPlusTree;

let mut index = BPlusTree::new();
index.insert(3_u32, "three");
index.insert(1, "one");
index.insert(2, "two");

assert_eq!(index.get(&2), Some(&"two"));
assert_eq!(index.get(&9), None);
assert_eq!(index.len(), 3);
```

`insert` returns the value it displaced when a key is overwritten, so a caller
can tell an update from a fresh insert without a second lookup:

```rust
# use index_db::BPlusTree;
# let mut index = BPlusTree::new();
assert_eq!(index.insert(1_u32, "one"), None);      // new key
assert_eq!(index.insert(1, "ONE"), Some("one"));   // replaced
```

The full surface is `new`, `insert`, `get`, `contains_key`, `len`, `is_empty`,
`height`, `clear`, and a `Default` impl. `get` and `contains_key` need `K: Ord`;
`insert` also needs `K: Clone`, because a leaf split copies a separator key up
into its parent. Values carry no bounds at all.

### Automatic splitting and balance

The whole point of a B+tree is that it manages its own shape. When an insert
fills a leaf past its capacity the leaf splits in two and promotes a separator
key to its parent; when that cascades to the root, the tree grows one level
taller. A leaf split *copies* its separator up — the entry it names still lives
in the leaf, where lookups must find it — while an internal split *moves* its
median up, since an internal separator is pure routing with no value attached.
Every leaf stays at the same depth, so the height tracks the logarithm of the
entry count: a million keys stand four levels tall.

```rust
# use index_db::BPlusTree;
let mut index = BPlusTree::new();
for k in 0..1_000_000_u32 {
    index.insert(k, k);
}
assert_eq!(index.height(), 4);
```

### Page-oriented node layout

Children are stored inline in their parent rather than behind individual heap
pointers, so a downward traversal walks contiguous memory with one fewer
allocation per node and better cache behaviour. A leaf keeps its keys and values
in two parallel arrays, so a search binary-searches only the keys and never pays
to load the values it skips. The fan-out is fixed so a node maps cleanly onto a
fixed-size page — the shape a pager will persist when `page-db` integration lands
later in the 0.x series.

### `no_std` support

The crate depends only on `alloc`; the default `std` feature only pulls in the
standard prelude. It builds for a `no_std` target with
`default-features = false`.

## Performance

Point lookups, measured with Criterion on Windows x86_64 (release, single
thread), against a pre-built tree:

| Tree size | `get` |
|-----------|-------|
| 1,000 | ~9.8 ns |
| 100,000 | ~26 ns |
| 1,000,000 | ~52 ns |

Building a tree of 1,000 keys from scratch (the insert-and-split path) runs at
roughly 17 ns per entry amortized. The growth from 10 ns to 52 ns across three
orders of magnitude is cache behaviour, not algorithmic cost — the height only
moves from 2 to 4 levels. Benchmarks live in `benches/index_bench.rs`; run them
with `cargo bench`.
